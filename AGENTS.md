# Project preferences

## Historical backups

- Treat substantial layout, visual-system, content-architecture, or deployment changes as major revisions.
- Before a major revision, preserve the current stable `main` commit as a dated GitHub tag or release.
- After the major revision is published and verified, preserve the new stable commit as another dated GitHub tag or release.
- Use the naming format `history-YYYY-MM-DD-short-description` and include a concise summary of what makes the snapshot significant.
- Never move or overwrite an existing historical tag. Create a new dated snapshot instead.
- Small typo, copy, spacing, or metadata fixes do not require a historical snapshot unless the user asks for one.
